同时用几个 Agent 写代码、查资料、做研究，很快会遇到一个尴尬的问题：每个 Agent 都要重新认识你一次。你把项目背景讲给 A，换到 B 又要讲一遍；A 昨天踩过的坑，B 今天还会再踩。

问题不在模型能力，而在**上下文没有共享**。这篇文章整理我为此搭的一套结构：以本地 Markdown 为权威数据，以 MCP 为统一读写接口，让多个 Agent 看到同一份项目状态和记忆。

## 问题：每个 Agent 都在重新认识你

最初的用法很自然：每个 Agent 各自维护聊天记录，需要背景时就把之前的对话粘过去。短期能用，长期有三个问题：

- 上下文越粘越长，真正有用的信息被淹没。
- 同一个事实在不同 Agent 那里有不同版本，互相冲突。
- 踩坑经验留在某次对话里，下次任务无法复用。

要解决的不是“让模型更聪明”，而是“让上下文有一个共同的存放位置”。

## 四层模型

我把整个系统拆成四层：

1. **多个 Agent**：编程、研究、日常助手，各自负责不同类型的任务。
2. **统一读写接口**：通过 MCP 暴露检索、记忆、项目状态等能力。
3. **共享上下文层**：个人偏好、项目状态、知识经验、执行历史。
4. **数据底座**：本地 Markdown + Git，可读、可迁移、可版本管理。

关键原则是：**Markdown 是权威来源，索引是可重建的辅助数据**。无论 Agent 怎么换，数据都在同一份文件里。

## 五类记忆

不是所有信息都值得长期保存。我把记忆分成五类：

| 类型 | 保存什么 | 作用 |
| --- | --- | --- |
| 个人记忆 | 稳定偏好、目标、技术背景 | 告诉 Agent 怎样的工作方式更适合我 |
| 项目记忆 | 目标、状态、技术栈、待办 | 告诉 Agent 现在做到哪里了 |
| 程序性记忆 | 已验证的流程和方法 | 告诉 Agent 下次应该怎么做 |
| 语义知识 | 原理、概念、研究结论 | 回答“是什么、为什么” |
| 情景记忆 | 某次任务实际发生了什么 | 回答“以前发生过什么” |

一个重要的取舍：**不要把历史对话原封不动地当长期记忆**。原始记录可以留档，但进入长期记忆之前，应该经过提炼、验证、去重和更新。

## 用 MCP 统一读写

MCP（Model Context Protocol）解决的是“不同 Agent 怎么用同一套工具”的问题。第一版只暴露 7 个工具，覆盖最常用的读写：

- `search_knowledge`：检索知识
- `get_memory`：读取某类记忆
- `get_project_context`：获取项目上下文
- `save_memory_candidate`：保存候选记忆
- `update_project_status`：更新项目状态
- `record_decision`：记录决策
- `get_task_context`：组装任务上下文包

工程上有一条原则：**业务逻辑写成普通函数，MCP 工具只负责校验输入、调用函数、返回结果**。这样核心逻辑可以单独测试，不依赖协议层。

## 记忆写入闭环

记忆不是写进去就完了，需要一个闭环：

1. 执行任务。
2. 提取候选经验：用户纠正、成功步骤、失败原因、技术决策。
3. 验证与审核。
4. 写入对应记忆。
5. 下次任务自动复用。

其中第 2 步最容易做错。如果让 Agent 自由写入长期记忆，很快就会积累大量未经证实的结论。所以我的做法是：Agent 只能写“候选记忆”，必须带来源；正式知识和长期偏好需要审核后才能晋升。

## 权限分级

不同操作的破坏力不同，权限也应该不同：

| 操作 | 级别 |
| --- | --- |
| 搜索、读取、获取上下文 | 全自动 |
| 保存候选记忆 | 自动，但必须带来源 |
| 更新项目状态 | 校验后执行 |
| 晋升候选记忆、修改长期偏好 | 仅本地 CLI，需人工审核 |
| 删除、批量重写、外发 | 必须显式授权 |

这套分级的核心是：**读取可以激进，写入必须保守**。检索结果只当资料，不当指令，也能降低提示注入的风险。

## MVP 验收清单

一个共享记忆系统是否真的工作，不看工具有多少，而看几个具体场景：

- Agent A 能读取项目状态，返回目标、状态和待办。
- Agent A 能搜索历史知识，返回真实路径、片段和状态。
- Agent A 能保存候选记忆，但不会覆盖正式知识。
- Agent B 能直接读取 Agent A 的新记忆，不需要复制聊天记录。
- 修改后的笔记能被重新检索，索引会检测变化并更新。
- 冲突和失败有可恢复记录，不会静默丢数据。

第 4 条是真正的里程碑：**两个 Agent 不复制聊天记录，也能共享同一份项目上下文。**

## 小结

- 多 Agent 的核心问题不是模型，而是共享上下文。
- 本地 Markdown 做权威数据，索引做可重建的派生数据。
- 用 MCP 统一读写，把业务逻辑和协议层分开。
- 记忆写入要经过候选、验证、晋升，不能自由改写长期记忆。
- 权限分级：读取激进，写入保守。
