“个人知识库”最容易掉进的坑，是一开始就把 RAG 全家桶装齐：向量数据库、Embedding 模型、重排模型、编排框架，一个不少。结果数据还没积累多少，维护成本先上来了。

我的做法相反：先用最小可用的关键词检索跑起来，等真实问题证明它不够用，再逐层替换。

## 文件即知识

知识库的底座是本地 Markdown 文件。选择它的理由很实际：

- 任何脚本都能直接遍历读取，不需要导出或同步。
- Git 可以做版本管理和备份。
- 数据不被某个云服务锁定，迁移成本低。
- 人和 Agent 都能读写同一份内容。

检索层是建立在文件之上的派生能力。文件是权威，索引和向量都可以重建。

## 起步方案与进阶替换

| 环节 | 起步选择 | 进阶替换 |
| --- | --- | --- |
| 知识底座 | 本地 Markdown | 加同步或发布 |
| 关键词检索 | SQLite FTS5 + 双字切分 | 专用中文分词器 |
| 向量数据库 | 暂不启用 | Chroma / Qdrant / Milvus |
| Embedding | 暂不启用 | bge-m3 |
| 重排 | 暂不启用 | bge-reranker |
| 编排框架 | 普通函数 | LlamaIndex / LangChain |
| 快速原型 | 自写 CLI | Dify / FastGPT |
| Agent 接入 | MCP | 远程 MCP + 认证 |

这张表的重点不是“最终都要上”，而是**每一层都有明确的替换触发条件**。

## 为什么先做 FTS5

关键词检索有三个现实优势：

1. **零模型成本**：不需要 GPU、不需要调用外部 API，本地 CPU 就能跑。
2. **结果可解释**：命中了哪些词、为什么排在前面，都能说清楚。
3. **建立基线**：先有一版能用的检索，才能用真实问题评估“向量检索到底带来了多少提升”。

很多个人知识库的查询其实是“我知道自己写过某个词”。这类需求用 FTS5 已经足够，没必要为了“语义搜索”而引入一整套向量基础设施。

## 向量检索的定位

向量检索擅长的是另一类问题：

- 记得意思但记不住原词，比如“那篇讲怎么避免过度设计的文章”。
- 同义表达、跨语言、模糊描述。
- 关键词命中率低，但语义相近的内容。

它的代价也很明确：

- 需要 Embedding 模型，模型变更后要重建全部向量。
- 需要向量库，多一个服务和一份存储。
- 相似度阈值、分块策略、重排都需要调参。
- 结果不如关键词检索直观，排查成本更高。

所以我的顺序是：**先用 FTS5 建立基线，用真实问题测试，确认关键词检索不够用，再接入向量检索。**

## 可插拔的语义后端

为了避免以后大改，我在检索层预留了一个语义后端接口：

```python
from typing import Protocol

class SemanticBackend(Protocol):
    def search(self, query: str, limit: int) -> list[dict]:
        ...

class NullBackend:
    def search(self, query: str, limit: int) -> list[dict]:
        return []
```

默认使用 `NullBackend`，也就是完全不启用语义检索。需要时再实现一个基于 Chroma 或 sqlite-vec 的后端，并在配置里切换。

这样做的好处是：调用方不需要知道底层是关键词还是向量，替换时只改配置，不改业务代码。

## 避免过度设计

几个我刻意没有做的事：

- 没有一开始就上多 Agent 编排框架。先把共享上下文和检索做好，再谈编排。
- 没有把所有聊天记录都向量化。原始历史、结构化记忆、知识文档应该分开处理。
- 没有追求“一次理解所有底层原理”。围绕真实项目逐层补，缺什么学什么。
- 没有为了未来的规模提前分库分表。个人知识库的数据量远没到那个阶段。

## 什么时候该升级

可以用几个信号判断：

- 真实问题测试集里，关键词检索的召回率持续低于可接受水平。
- 用户开始频繁用“意思相近但词不同”的方式提问。
- 同一主题的内容分散在多篇笔记里，关键词只能命中其中一部分。

在这些信号出现之前，升级向量检索只是增加复杂度，不会带来实际收益。

## 小结

- 本地 Markdown 是可靠的底座，索引和向量都是可重建的派生数据。
- 先上 FTS5，建立可解释、可评估的检索基线。
- 向量检索解决的是另一类问题，不应该成为默认起点。
- 用接口隔离语义后端，让升级变成替换而不是重写。
